# Working agreement

Start with the [takeover guide](docs/CLAUDE-HANDOFF.md) for the game, image generation, backgrounds, audio and release workflow.

- In every user-facing label, call the games **Rätsel** and their individual tasks **Aufgaben**. Keep internal IDs, routes, save keys and historical review records stable.

- Read [current design](design/README.md), [visual style](design/VISUAL-STYLE.md), [puzzle blueprint](design/PUZZLE-BLUEPRINT.md) and [Rätsel layout](design/RAETSEL-LAYOUT.md) before changing the game. Propose appearance changes first as a Heute/Vorschlag comparison of every distinct screen ([tools/raetsel-ansichten](tools/raetsel-ansichten/README.md)) and implement them after the owner's sign-off.
- Build on the shared current renderers. Every puzzle uses five distinct iterations, no hints/timer, common feedback/celebration and individual adult review. Do not generate or ship editorial approvals.
- Keep learning subjects and ALL UI character portraits in the canonical painted style. Letters, puzzle context, map pins, menus, companions and celebrations use the same painted cast through `FK.friendsArt.portrait`; the freely explorable world keeps its 3D models. Task utility controls use the shared SVG family. World controls and all navigation backs use simple illustrated symbols. The map den marker matches the painted animal pins; the exit sign uses the same simple illustrated outlines and flat fills as map/letter/settings (`exit-symbol` prompt), never a geometric SVG substitute. The map dialog has no header icons and closes on an outside tap or Escape; dragging/panning must keep it open. Fonts: Andika for learning/controls/body; Baloo 2 for menu headings.
- The shared painted atlas includes Reh, Igel, Steinbock and the sleeping Fuchs. `FK.friendsArt.letterPortrait` uses that same atlas. Use `friend-portraits` or `fox-sleep-portrait` for new work. The adopted runtime map is version 2: simplified flat 2D, strict top-down view, broad woodland areas and clear routes/water. Keep geography, calibrated world-to-painting positions and non-overlapping picture-only 64 px pins consistent on the 880 px minimum board; use `world-map` and `node tools/map/layout.cjs --check`. Model renders and old geometry maps are development references, never replacements for the painted UI assets.
- For EVERY image-generator request, read the [canonical illustration style](design/illustrations/STYLE.md), `waldpost-watercolour-pencil-v1`. Run `node tools/illustrations/style.cjs --request <id>` and pass its complete prompt, actual reference images and transparency flag to the available service. Keep the two fixed canonical images first; additional current targets define content/composition only. Follow the prescribed navigation/scene/stationery detail levels within the same style.
- Reuse the [central image library](assets/waldatelier/README.md). Follow the [illustration workflow](design/illustrations/README.md) and [artwork handoff](design/artwork/README.md). Edit subject/layout briefs, regenerate all complete prompts, then run `node tools/illustrations/style.cjs --check`. Never copy archived style language, use superseded images as style inputs or treat a historical generation record as a forward prompt. Retain the actual new request, references, source and preparation metadata. Report a missing image-generation capability honestly.
- Preserve save keys, drawing template IDs, offline/update behaviour and archived originals. Archive is historical reference, never a runtime dependency or competing specification.
- Preserve existing puzzle reviews across releases. Invalidate only iterations whose actual question, difficulty, rule, interaction or rendered assets changed. Typography corrections retain approvals when the task, answers, interaction and pictures match. Menu text, competence summaries and unrelated iterations retain approvals. Derive a puzzle's release from all its iterations. Compare historical content and per-iteration presentation before restoring original GitHub decisions read-only. Retain later restrictions, comments, dates and deletion markers. Never rewrite the review-data branch as part of a code deployment.
- Run the relevant checks in [Development](docs/DEVELOPMENT.md), regenerate the puzzle catalogue/fingerprint and update the consistency audit after visual changes.
- Work on a branch and push useful checkpoints. Changes go to `dev` (the development version at …/dev/, with Rätsel review); `main` is the children's version with only the released Rätsel and no review function ([channels](docs/CHANNELS.md)). Release `dev` to `main` only when the user authorizes it and every Rätsel is approved, regenerating `js/friends/released.js` with `node tools/release-manifest.cjs`. Session instructions take precedence over older documents.
